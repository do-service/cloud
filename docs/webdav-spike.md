# E0-9. Прототип WebDAV на `x/net/webdav`

**Дата:** 2026-10-23 · **Риск:** A1 в [architecture.md](architecture.md) · **Библиотека:** `golang.org/x/net v0.61.0`, пакет `webdav` (BSD-3, совместима с Apache 2.0)

## Вердикт

**Библиотеку берём, но в E7-1 форкаем хендлер.** Протокольное ядро у неё рабочее: litmus почти полностью зелёный, rclone работает, PUT стримится. Но для продакшена не хватает расширяемости: у `LockSystem` и `DeadPropsHolder` нет `ctx`, ошибки нельзя сопоставить со статусами, PUT не поддерживает условные заголовки, а PROPFIND ходит в FS по одному разу на каждый дочерний узел. Обёртками это не исправить.

План для E7-1: скопировать в `internal/webdav` файлы `webdav.go`, `prop.go`, `if.go` и часть `lock.go` (около 1,5 тыс. строк) с сохранением BSD-заголовка. XML-слой (`xml.go` и `internal/xml`) использовать из библиотеки, не форкая. Свой слой с нуля не нужен.

> **Поправка после E7-1:** XML-слой библиотеки взять нельзя — функции `xml.go` неэкспортируемые, а `golang.org/x/net/webdav/internal/xml` не импортируется снаружи `x/net`. В E7-1 он написан заново на `encoding/xml`; из библиотеки взяты `if.go`, подтверждение блокировок и `MemLS`. Прототип (`SpikeFS`, `WEBDAV_SPIKE_DIR`) удалён; инструкции ниже — история.

## Что сделано

- `backend/internal/webdav`: обёртка `New` (403 `propfind-finite-depth` на `Depth: infinity` и на PROPFIND без Depth) и `SpikeFS` поверх `webdav.Dir`. В `SpikeFS`: ETag и `oc:fileid` из inode, `getcontenttype` по расширению без чтения файла, `quota-*` для папок, dead properties в памяти.
- Маршруты `/dav/files/spike/` и `/remote.php/dav/files/spike/` включаются **только** через `WEBDAV_SPIKE_DIR` (по умолчанию выключено; с E2-4 — за Basic auth паролем приложения любого пользователя, дерево общее).
- Тесты: `backend/internal/webdav/webdav_test.go`. `TestLibraryGaps` фиксирует недостатки библиотеки — если обновление их изменит, тест упадёт и документ нужно будет пересмотреть.

Как воспроизвести:

```sh
WEBDAV_SPIKE_DIR=/data/dav-spike docker compose up -d --build
docker run --rm --network cloud_default debian:trixie-slim sh -c \
  'apt-get update -qq && apt-get install -y -qq litmus && litmus http://cloud:8080/dav/files/spike/'
# litmus останавливается на первом наборе с падениями; остальные: -e TESTS="locks http"
```

## Результаты

### litmus (против контейнера)

| Набор | Итог | Падения |
|-------|------|---------|
| basic | 16/16 | — |
| copymove | 13/13 | — |
| props | 29/30 | `propfind_invalid2`: тело с неверным объявлением namespace принимается (207 вместо 400). Безвредно, это известный пункт FAQ litmus |
| locks | 32/34 (7 пропущено) | `lock_shared`: **shared-блокировки не поддерживаются** (501); `fail_complex_cond_put`: составное условие в `If` не отклоняется (201 вместо 412); предупреждение `cond_put_with_not`: 412 вместо 423 |
| http | 4/4 | — |

Алиас `/remote.php/dav/…` проходит basic на 16/16.

### rclone (`vendor=other`)

- `copy` 202 файлов: кириллица, пробелы, эмодзи, вложенность и файл 1 ГБ. `check` и `check --download`: 0 расхождений.
- `sync` с изменением, добавлением и удалением файла отрабатывает корректно; `moveto` папки выполняется на сервере (MOVE).
- **Пик памяти контейнера при заливке 1 ГБ — ~47 MiB**: PUT стримится, а не буферизуется.
- Хэши не сверяются («hashes could not be checked»): контрольных сумм в свойствах нет. Для Nextcloud-режима клиентов понадобится `oc:checksums` (P1).

## Что требование из architecture §8 даёт в библиотеке

| Требование | Как в `x/net/webdav` | Что делать в E7 |
|------------|----------------------|-----------------|
| `getetag` файла | `ETager` на `FileInfo` | использовать как есть |
| `getetag` **папки** | библиотека его **не отдаёт** вовсе (`dir: false` в `liveProps`) | в прототипе обходим через `DeadProps`; в форке сделать живым свойством |
| `oc:fileid`, `quota-used-bytes`, `quota-available-bytes` | своих живых свойств добавить нельзя; работает только через `DeadPropsHolder` (без `ctx`) | живые свойства в форке |
| `getcontenttype` | `ContentTyper`, иначе библиотека читает 512 байт каждого файла | обязательно реализовать (S3!) |
| Запрет `Depth: infinity` | библиотека обходит всё дерево | обёртка (уже есть) |
| LOCK в Postgres | у `LockSystem` **нет `ctx`**; `Confirm` держит блокировку до `release()`, как in-process мьютекс; shared-блокировок нет; `lockdiscovery` не отдаётся | своя `LockSystem` на таблице `locks` с `ctx` в форкнутом интерфейсе; `Confirm` — `SELECT … FOR UPDATE` в транзакции запроса |
| Большой PUT | стримит через `File.Write`, ошибку `Close()` обрабатывает | финализация в `Close()` (как tus) ложится естественно |
| Условный PUT | `If-Match` и `If-None-Match` игнорируются (TODO в коде); перезапись отвечает 201 вместо 204 | в форке; без этого sync-клиент молча затирает чужие изменения |
| Коды ошибок | ошибки записи в PUT превращаются в 405, ошибки открытия — в 404 или 409; квоту, права и чужую блокировку не отличить | в форке маппинг ошибок `fs` → 403, 404, 409, 412, 423, 507 |
| PROPFIND Depth 1 | **N+1**: на 50 файлов 52 `OpenFile` и 51 `Stat` (`TestPropfindDepth1FSCalls`) — по два обращения на каждый дочерний узел | в форке строить ответ из одного листинга; минимум — кэш листинга на время запроса в FS-адаптере |
| GET папки | 405 | достаточно |

Мелочь: PROPPATCH открывает цель с `O_RDWR`, и ОС отказывает для папок. В `SpikeFS` это обойдено, а в реальном `fs` проблемы не будет — там нет `os.OpenFile`.

## Не проверено

- Windows (Mini-Redirector), macOS Finder, davfs2, GNOME/KDE и мобильные клиенты — по плану это ручной чек-лист E7-5. Дерево прототипа общее для всех пользователей, поэтому подключать его к реальным клиентам рано.
- Нагрузка: PROPFIND на 50 000 элементов (G2) — после E1-4, на реальном `fs`.
