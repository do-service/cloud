# Бенчмарк-стенд (E1-8)

Синтетическое дерево на 20 млн узлов и 2 000 пользователей плюс k6-сценарии
листинга. Цели — из `docs/prd.md` (G2, таблица метрик) и
`docs/architecture.md` (таблица бенчмарков, риски A3/A6).

| Сценарий | Что делает | Порог |
|---|---|---|
| `k6/listing-50k.js` | 6 VU, каждый пролистывает папку на 50 000 элементов до конца в своей сортировке (`name`/`mtime`/`size` × `asc`/`desc`), страница по умолчанию — 200 | p95 < 200 мс и для первой страницы (`{page:first}`, это G2), и для всех; 0 ошибок; ни один элемент не пропущен и не повторён |
| `k6/workday.js` | рост до 400 VU за минуту, удержание `HOLD` (5 мин), спад; каждый VU — свой пользователь, открывает случайные папки своего дерева, иногда листает дальше, думает 1–3 с | p95 листинга < 300 мс, 0 ответов 5xx |
| `k6/search.js` | 50 VU минуту ищут по имени (R5): частые слова (сотни совпадений на пользователя), редкие и промахи | p95 < 300 мс, все ответы 200 |

Время — от k6 до сервера на той же машине, то есть серверное плюс loopback.

## Генератор

`backend/cmd/benchgen` (флаги: `go run ./cmd/benchgen -h`):

- накатывает миграции и **отказывается** работать с базой, где уже есть
  пользователи (`-allow-existing` — только для заведомо тестовой базы);
- узлы делятся между пользователями по лог-нормальному закону (несколько
  «тяжёлых», длинный хвост лёгких); в дереве ~10% папок, глубина до 9 уровней
  папок (файлы — на уровень глубже), файлы раскиданы по папкам неравномерно;
  имена кириллические и латинские, размеры и даты правдоподобные;
- у первых `-big-dirs` пользователей (по умолчанию 1) — «Большая папка» ровно
  на 50 000 элементов (1% из них — пустые папки, чтобы листинг пересекал
  границу «папки, потом файлы»);
- размеры папок — сумма поддерева, как их поддерживает fs-сервис;
  `users.used_bytes` — размер корня;
- у файлов есть строка `blobs` с бэкендом `s3` и несуществующим ключом:
  листинг работает, скачивание — нет, на диск ничего не пишется;
- каждому пользователю — сессия на 10 лет; сырые токены пишутся в
  `bench/tokens.jsonl` (JSON на строку: `userId`, `token`, `rootId`,
  `bigDirId`, `dirs` — корень и до 20 случайных папок). Файл в `.gitignore`;
- одинаковые `-seed` и размеры дают одинаковые строки.

На время загрузки индексы и ограничения `nodes`/`blobs` снимаются и потом
строятся заново по определениям из самой базы. Если запуск прервался,
остаётся таблица `benchgen_pending_schema`, и следующий запуск откажется
работать: базу нужно пересоздать.

## Запуск

```sh
docker compose up -d postgres
docker compose exec -T postgres psql -U cloud -d cloud -c 'CREATE DATABASE cloud_bench'

cd backend
make bench-gen                              # 20 млн узлов; BENCH_FLAGS='-nodes 300000' — быстрый вариант
make bench-server                           # сервер на :8091 поверх cloud_bench (отдельный терминал)
make bench-listing                          # k6/listing-50k.js
HOLD=1h make bench-workday                  # k6/workday.js, PRD требует час
env -u HTTP_PROXY -u HTTPS_PROXY k6 run ../bench/k6/search.js   # поиск (R5)
```

Переменные k6: `BASE_URL` (по умолчанию `http://localhost:8091`),
`COOKIE_NAME` (`session`; `__Host-session`, если `PUBLIC_BASE_URL` — https),
`TOKENS` (путь к файлу токенов, относительный — от `bench/k6/`),
`VUS`/`HOLD` для workday, `PASSES` и `BIG_DIR_SIZE` для listing-50k.
`make bench-*` снимает `HTTP_PROXY`/`HTTPS_PROXY`: k6 их учитывает, и
прокси перед localhost попал бы в замер.

Чтобы бенчмарк гонять повторно, базу не нужно пересоздавать: k6 только
читает (сервер лишь продлевает сессию — одна запись на пользователя в час
использования, на замер это не влияет).

## Размер и время

Полный набор (20 млн узлов, 2 000 пользователей) на MacBook (10 ядер,
Postgres 18 в Docker Desktop с настройками по умолчанию, `-workers 6`):

| | |
|---|---|
| Генерация | ~4 мин: загрузка 1 мин (~360 тыс. узлов/с), индексы и FK 3 мин (дольше всех trigram — 2 мин), VACUUM 20 с |
| `pg_database_size` | ~15,5 ГБ: `nodes` 12 ГБ (таблица 5,5 ГБ, индексы остальное), `blobs` 3 ГБ |
| Состав | 2 млн папок, 18 млн файлов; у пользователя от ~300 до ~160 тыс. узлов |

Свободного места нужно с запасом на WAL — от 20 ГБ.

В CI (`backend:bench` в `.gitlab-ci.yml`) — 2 000 пользователей и 300 000
узлов с той же папкой на 50 000 и тем же порогом G2; полный размер и
workday запускаются вручную.

## Дерево для синхронизации (E11-2)

`GET /api/v1/sync/tree` — NDJSON всего поддерева в одной `REPEATABLE READ`
транзакции, по уровням, страницами по 5 000 строк (индекс `nodes_name_key`).
Замер: `benchgen -users 1 -nodes 500001` (один пользователь, «Большая
папка» на 50 000), отдельный сервер на той же машине, `curl` с cookie,
тело в файл; три прогона, тёплый кэш:

| Корень | Строк | Ответ | Время | Скорость |
|---|---|---|---|---|
| «Большая папка» | 50 000 | 17,7 МБ | ~0,2 с (первый прогон 0,6 с) | ~250 тыс. строк/с |
| корень пользователя | 500 000 | 173 МБ | 2,7–3,7 с | ~150–185 тыс. строк/с |

Первая строка (курсор) приходит через 15–30 мс. Узкое место — кодирование
JSON и передача, не запросы: страница на 5 000 строк — ~25 мс в Postgres.

## Загрузка (E3-9)

Цель G1 из `docs/prd.md`: файл 10 ГБ грузится со скоростью не ниже 90%
канала 1 Гбит/с, после обрыва загрузка продолжается без потери
загруженного. Меряется один поток tus так, как грузит веб-интерфейс
(`frontend/src/uploads.tsx`): чанки по 64 МиБ, один PATCH на чанк, при
сетевой ошибке или 5xx — HEAD за смещением сервера и продолжение с
задержками tus-js-client (0, 1, 3, 5, 10, 20, 30 с). По результату
решается, нужны ли параллельные чанки (E3-4).

Клиент — `backend/cmd/benchupload` (флаги: `go run ./cmd/benchupload -h`):

- содержимое генерируется на лету (ChaCha8 блоками по 1 МиБ, ключ —
  `-seed` и номер блока): на диск клиента ничего не пишется, данные не
  сжимаются, любое смещение воспроизводится заново при докачке.
  Генератор — ~1 ГБ/с в контейнере, в 8 раз быстрее канала;
- sha256 считается отдельным проходом до загрузки (`hashSeconds`, в замер
  не входит) и уходит в метаданных `sha256`: сервер сверяет его при
  финализации, так что потерянный или повторённый при докачке байт
  проваливает прогон;
- `-break-at 0.5` — на этой доле клиент обрывает идущий PATCH посреди
  чанка (отменяет запрос, соединение закрывается) и продолжает через HEAD;
- после успеха файл удаляется в корзину и из неё (`-cleanup=false` —
  оставить), после неудачи удаляется незаконченная загрузка;
- в конце — сводка и строка JSON: `transferSeconds` (от первого PATCH до
  последнего отданного в соединение байта), `finalizeSeconds` (от него до
  ответа, завершающего загрузку: сервер сверяет хэш и коммитит узел), `totalSeconds` (от POST), `mbps`/`pctOf1Gbit` по
  передаче и `mbpsTotal`/`pctOf1GbitTotal` от начала до конца (МБ = 10⁶
  байт, 1 Гбит/с = 125 МБ/с), `resumes` (сколько было отправлено к обрыву
  и сколько сервер сохранил), `resentBytes`, `nodeId`, `sha256Ok`.
  Код выхода ненулевой при любой ошибке, в том числе несовпадении хэша.

Канал эмулируется так: клиент работает в контейнере `bench-upload`
(профиль `bench` в `docker-compose.yml`, `bench/upload/Dockerfile`) рядом
с `cloud` и сам ограничивает свой исходящий трафик —
`tc qdisc replace dev eth0 root netem delay $RTT rate $RATE limit 200000`
(`bench/upload/shape.sh`, нужен `NET_ADMIN`). Задержка только на стороне
клиента: данные задерживаются, ACK — нет, RTT ≈ `delay`. Очередь netem по
умолчанию (1000 пакетов) меньше произведения 1 Гбит/с × 50 мс, потери из
неё выглядели бы как медленный канал — отсюда `limit 200000`. `RATE` по
умолчанию `1gbit` (пусто — без ограничения), `RTT` — `0`. Перед запуском
скрипт печатает qdisc и `ping cloud`.

### Запуск

Нужен пользователь с квотой больше размера файла и ~11 ГБ свободного
места в томе `cloud_data` (`docker compose exec cloud df -h /data`): файл
целиком лежит в `uploads/tus`, потом переезжает в дерево. Вход:

- `SESSION` — значение cookie `session` любого пользователя (OIDC тоже:
  взять из браузера или из cookie jar после входа curl-ом);
- или `BENCH_USER`/`BENCH_PASSWORD` — локальный пользователь, например
  первый админ (`ADMIN_USERNAME=… ADMIN_PASSWORD=… docker compose up -d` на
  пустой базе).

Переменные берутся из окружения и в аргументы процесса не попадают.

```sh
docker compose up -d --build
cd backend
export SESSION=…                            # или BENCH_USER / BENCH_PASSWORD
make bench-upload                           # RTT 0, 20 мс, 50 мс по очереди; RTTS='0 50ms' — свой набор
make bench-upload-resume                    # обрыв на половине; RTT=50ms — с задержкой
make bench-upload-restart                   # docker compose restart cloud, когда на сервере 2 000 МБ (RESTART_AT_MB)
UPLOAD_FLAGS='-size 4GiB' make bench-upload # файл поменьше
```

Клиент не ходит через прокси (`HTTP(S)_PROXY` не учитывается), так что
снимать их, как для k6, не нужно.

### Результаты

MacBook (M1 Max, 10 ядер), Docker Desktop (VM на ядре 7.0 linuxkit, 10
CPU, 16 ГБ), клиент и сервер в одной VM, файл 10 ГиБ (10 737 418 240
байт), чанк 64 МиБ. Числа приблизительные: диск, CPU и «сеть» —
одной машины. Настоящий замер G1 — на Linux-хосте с реальным каналом
1 Гбит/с.

До хэша на лету (финализация перечитывала файл):

| RTT (netem) | ping | Передача, с | Финализация, с | Всего, с | МБ/с (передача) | % от 1 Гбит/с | МБ/с (всего) | % (всего) |
|---|---|---|---|---|---|---|---|---|
| без ограничения | 0,4 мс | — | — | — | ~970 (1 ГиБ) | — | — | — |
| 0 | 0,12 мс | 90,5 | 7,2 | 97,7 | 118,7 | **95%** | 109,9 | 88% |
| 20 мс | 27–40 мс | 93,6 | 6,3 | 99,9 | 114,7 | **92%** | 107,5 | 86% |
| 50 мс | 53–101 мс | 187,4 | 6,4 | 193,9 | 57,3 | **46%** | 55,4 | 44% |
| 50 мс, `tcp_wmem` до 16 МБ у клиента (4 ГиБ) | 51–103 мс | 39,5 | 2,2 | 41,9 | 108,6 | 87% | 102,6 | 82% |

После (sha256 считается при приёме PATCH, финализация файл не читает):

| Прогон | Передача, с | Финализация, с | Всего, с | % от 1 Гбит/с (передача) | % (всего) | sha256 |
|---|---|---|---|---|---|---|
| RTT 0, 10 ГиБ | 90,2 | 0,21 | 90,4 | **95%** | **95%** | ✅ |
| `-break-at 0.5`, RTT 0, 4 ГиБ | 36,1 | 0,04 | 36,1 | 95% | 95% | ✅ |
| `restart cloud` на 1 000 МБ, RTT 0, 4 ГиБ | 41,9 | 0,08 | 42,0 | 82% (с простоем рестарта) | 82% | ✅ |

| Докачка | Отправлено к обрыву | Сервер сохранил | Отправлено повторно | Всего, с | sha256 |
|---|---|---|---|---|---|
| `-break-at 0.5`, RTT 0 | 5 402 263 552 | 5 402 263 552 | 0 | 96,6 (95% по передаче) | ✅ |
| `-break-at 0.5`, RTT 50 мс, 2 ГиБ | 1 107 296 256 | 1 107 296 256 | 0 | — | ✅ |
| `restart cloud` на 2 ГБ, RTT 0 | 2 147 483 648 | 2 147 483 648 | 0 | 101,2 (90% по передаче) | ✅ |

Что видно:

- **Потолок канала — 95%, не 100%.** netem считает байты кадра, а полезная
  нагрузка TCP в кадре 1514 байт — 1448: 1448/1514 × 125 МБ/с ≈ 119,6 МБ/с.
  Столько же даст настоящий гигабитный Ethernet, так что 90% от 1 Гбит/с —
  это 95% от достижимого.
- **RTT 0 и 20 мс: один поток укладывается в G1** (95% и 92% по передаче).
  Чанки почти не мешают: на каждый 64 МиБ — пауза в один RTT на ответ
  (20 мс к ~0,56 с передачи — ~3%) и повторный разгон окна после паузы.
- **RTT 50 мс: 46% — упор в буфер отправки TCP клиента, не в сервер и не в
  tus.** Linux по умолчанию растит `tcp_wmem` до 4 МБ, а
  1 Гбит/с × 50 мс ≈ 6,25 МБ; с потолком 16 МБ тот же клиент даёт 87%.
  Оставшиеся ~8% — пауза в RTT на каждый чанк и разгон после неё. Буфер
  отправки — настройка ОС клиента (у браузера свои автонастройки, у
  macOS и Windows другие пределы), сервер его не изменит; приёмный буфер
  сервера (`tcp_rmem` до 32 МБ) не мешал.
- **Финализация** была 6–7 с на 10 ГиБ (~1,6 ГБ/с: повторное чтение файла
  для sha256 и коммит), 6–7% от общего времени, и по общему времени G1 не
  выполнялась уже при RTT 0 (88%). Теперь хэш считается на лету при приёме
  PATCH, состояние лежит рядом с данными (`{id}.sha256`) и переживает
  обрыв и рестарт сервера: финализация — 0,04–0,2 с, по общему времени
  95%. Повторное чтение осталось запасным путём, если состояние хэша
  разошлось с данными.
- **Докачка теряет ноль байт**: и при обрыве посреди чанка, и при
  перезапуске сервера смещение, которое вернул HEAD, совпало с
  отправленным, повторно ничего не ушло, хэш сошёлся. Оговорки: обрыв в
  эмуляции — штатное закрытие соединения (FIN, данные из буфера сокета
  доходят); выдернутый кабель или RST потеряли бы до размера буфера —
  клиент дошлёт их с HEAD-смещения, на результат это не влияет. При
  `docker compose restart` сервер дождался конца идущего PATCH
  (graceful shutdown, 15 с), клиент получил `connection refused` на
  следующем и через 1 с продолжил; смещение пережило рестарт, потому что
  tusd хранит загрузку файлом в томе `/data`.

Вывод для E3-4: при RTT до ~20 мс одиночный поток с чанками 64 МиБ даёт
G1 по скорости передачи; на 50 мс он упирается в TCP-окно клиента, и
параллельные чанки (или несколько соединений) — способ получить канал без
настройки ОС клиента. Стоит перемерить на настоящем Linux-хосте и
браузере, прежде чем решать.
